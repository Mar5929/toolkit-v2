+### Requirement 1: The checklist
+
+- **Original verbatim requirement:** "One is a checklist, about half a page, that I follow when a tester reports a bug." (Mike, in chat, 2026-10-09)
+- **Goal:** Mike handles every tester's bug report in the same way, and no report is lost.
+
+**Functional Requirements**
+
+1. The checklist is a numbered list of steps, in the order Mike does them. It starts when the report arrives and ends when the tester knows which build holds the fix.
+2. Each step starts with a verb and says one thing to do.
+3. The steps cover these five things, in this order: get the details of the report, look for the crash report, make the bug happen again, record the bug, and answer the tester.
+4. Where a step uses one of the project's tools or people, the checklist names it as the project's records name it: the "Feedback" tab of the beta tester sheet, Bea Hollis, Sentry, and a work item for the bug.
+5. The checklist is about half a page: 150 to 250 words.
+6. Does not apply to anyone but Mike: the checklist is for his own notes, and it is not sent to the testers or to anyone else.
+
+**Acceptance Criteria:**
+
+1. The checklist has between 150 and 250 words.
+2. Every step has a number and starts with a verb.
+3. The checklist has at least one step for each of the five things in Functional Requirement 3, in that order.
+4. Every tool and person that the checklist names is in `PROJECT.md` or in project memory, under the same name.

+# When a tester reports a bug
+
+## Checklist
+
+1. Check that the report has a row in the "Feedback" tab of Bea Hollis's sheet "Pocket Ledger beta testers". If the report came straight to you, ask Bea to add the row.
+2. Ask the tester for their phone model and iOS version. If the phone model differs from the tester's row in the "Testers" tab, tell Bea.
+3. Ask the tester, or Bea, for what else is missing: the build number, the steps taken, what the tester expected, what happened, and a screenshot.
+4. Search Sentry, project `pocket-ledger-ios`, for a crash report from that build at that time. Copy its link.
+5. Follow the tester's steps on the same build until the bug happens again. Try once without a connection.
+6. Write down the result: it happens every time, it happens sometimes, or it did not happen.
+7. Record the bug as a new work item, with the report, the Sentry link, and the steps. If a work item already covers the bug, add the report there.
+8. Set the priority. A crash or a lost transaction comes before a wrong display.
+9. Answer the tester, through Bea if she sent the report. Say what you found and what happens next.
+10. Tell Bea which build holds the fix, so that she tells the tester.
+
+## Sticky note
+
+1. Feedback row, then missing details
+2. Sentry, then repeat the bug
+3. Work item, then answer the tester
