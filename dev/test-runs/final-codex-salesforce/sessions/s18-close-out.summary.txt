## 1. Before anything ships

- The result approval is recorded (`toolkit work show <id>` shows
  `result_approved`), or the owner said "ship it" or "mark it done" after he
  saw the result, the gaps, and the evidence. Record that with his words
  (`approvals.md`, "Result approval").

- Done means the owner accepted the result. Cancelled means the work stopped
  without it.
- Stages that do not apply are skipped. Work with no repository change has no
  pull request; work with no deployment has no deployment stage. A skipped
  stage gets one history note saying so, so `toolkit work finish` has a
  record of it.

## 2. Commit, push, and the pull request (stage 12)

- Commit the item's files on its branch, staged by name
  (`claude/<prefix>-<number>-<slug>`, for example `claude/wi-007-csv-export`).
  No `Co-Authored-By` line naming an AI and no "Generated with" line.
- Push the branch. Never force-push.
- Write the pull request title and description in plain words: what changed,
  why, how it was checked, and the item id. Run the description through the
  `unslop` skill, because other people read it. No line crediting an AI.
- Set the stage:
  `toolkit work set <id> --stage 12-pr-and-push`
- In Codex, every Git write here needs the owner's approval and escalated
  permissions (`git-rules.md`).

## 3. Merging

Merge only through `merge-and-clean-up`, and only when one of these holds:

- the owner said yes to this merge; or
- a standing merge instruction applies (`approvals.md`, "Standing merge
  instruction"): it is recorded in `DECISIONS.md`, an `acceptance-checker`
  that did not build the change found no blocking issue on that exact head
  commit, and every check passes.

A work item that says its merge needs the owner's approval overrides a
standing instruction. Without an independent check, the standing instruction
does not apply: ask the owner.

A merge that stops on a conflict: resolve it and commit with a message you
write (`git commit -m 'Merge <branch>: <what it brings>'`). Never
`git commit --no-edit`: it keeps Git's "# Conflicts:" lines in the message.

# Memory save

Voice: write to the owner in plain English. Claude Code: follow the project's Plain English output style. Codex: follow the "How to write replies" section of `AGENTS.md`.
Saves, corrects, or retires one memory record with `toolkit memory` commands, or sends the fact to its proper home. It never edits memory files by hand.

## Steps

Track these steps in the host's plan tool (Claude Code: the task list; Codex: `update_plan`), not in the reply.

1. Decide the home with the memory criteria (`.memory/memory-criteria.md` with built-in memory, which wins; otherwise `references/memory-criteria.md`). Not memory: send it to its home ("Where other things go" below) and stop.
2. Search for a record that already holds it, and read each hit with its version. The save's duplicate check compares wording, so only this search finds a record the new fact contradicts (for example "Mondays" against "Tuesdays").
   `toolkit memory find '<topic>'`
   `toolkit memory get <key> --json`
3. Read the approval mode and apply "Approval policy" below. When it says ask, ask and wait.
   `toolkit config get memory.approval`
4. Write the description and body in the record format (`references/record-format.md`), then save with the form for the case ("Save forms" below).
5. Exit code 2 saved nothing. Read the "Error:" line. Records listed: the duplicate check. "Changed since it was read": read it again and redo the change. Any other rule: fix the text as the message says. `references/replacing-and-retiring.md`, section 2, has each case.
6. "Forget that": retire the record, with his words as the reason. Delete only when his own words say delete ("Approval policy").
   `toolkit memory retire <key> --reason '<his words>'`
7. An owner to-do with no work item, or a change to what is happening now: update the current focus (`references/current-focus.md`). A project term: update the glossary (`references/glossary.md`).
8. A preference a project setting can enforce (for example "I hate tabs" and `.editorconfig`): save it, then offer that change too.
9. Read the record back, check, and reply in one line ("Replies" below). End with the question still waiting for the owner, or the exact words that continue.
   `toolkit memory get <key>`
   `toolkit doctor`
