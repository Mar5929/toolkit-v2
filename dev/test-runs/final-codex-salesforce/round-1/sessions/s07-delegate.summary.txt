## Traversal Trick for Atlas Guides

Every atlas guide has a machine-readable table of contents. One fetch returns the entire link tree of the guide (every topic name and its page URL) plus the current release and API version:

```
https://developer.salesforce.com/docs/get_document/atlas.en-us.<guide-id>.meta
```

Then fetch any topic from the tree:

```
https://developer.salesforce.com/docs/atlas.en-us.<guide-id>.meta/<guide-id>/<topic-href>
```

- Use this to confirm the **current API version** at the start of any design session (the JSON reports it, e.g. "Summer '26 (API version 67.0)").
- To read an older release, pin the version in the URL: `atlas.en-us.<release>.0.<guide-id>.meta` (e.g. `atlas.en-us.256.0.apexcode.meta`).

## 1. What counts as approval

`toolkit work lifecycle` prints the gates and these rules. In short:

- Only the owner's explicit words count. Quote them in a history note.
- A question, a suggestion, a tentative answer ("probably B"), silence, or a
  saved draft is not approval.
- An approval covers only what was shown. It never covers merge, deployment,
  spending, or publishing.
- An approval survives later stages. A stage alone does not prove approval:
  check the approval field (`toolkit work show <id>`).
- A bare "yes", "ok", or "looks good" answers only a yes-or-no question asked
  earlier in this conversation. When none was asked, or the waiting question
  is not a yes-or-no question, show the decision with its choices and your
  recommendation, and record nothing.
- After a yes, save his words first, in a history note that starts with
  `Owner said:`. Then run the gate's commands. A command that refuses then
  never loses his answer, and no later session asks him again.

| The owner says | After this question | It is |
| --- | --- | --- |
| "Yes, approved." | "Do you approve these requirements?" | The requirements approval |
| "Go with B." | The design options with a recommendation | The choice and approval of Option B |
| "Looks good." | "Do you approve this result?" | The result approval |
| "Looks good." | "Shall I split WI-12 into these three sub-items?" | A yes to the split only, not a result approval |
| "ok" | Nothing was asked in this chat | Not an answer; ask what he wants |

# Design critic

Check one draft design. Report where it fails the requirements, the goal, or
the writing rules. You advise; the architect fixes; the owner decides. You
are never the agent that wrote the draft.

## Start with the brief

- The brief gives the work item id, the draft file path (Codex) or the whole
  draft pasted into the brief (Claude Code, where the architect writes no
  file), the design's opening sections and Notes (What this design solves,
  Requirements and design readiness, Constraints and assumptions, the owner's
  rulings in Notes > Design changes during the interview), the way of working
  the owner chose, and the requirements (Agreed goal, every `R-xx`,
  Acceptance). Read those first, then the draft.
  You do not inherit the conversation or another agent's findings.
- Treat only rulings the brief marks as approved by the owner as settled.
  Proposals and unanswered questions stay open. Do not infer approval for the
  rest of the draft.

## Check every requirement

For each requirement, one line:

- **Satisfied:** the draft names the mechanism, says why it meets the
  requirement, and says how to check it, and you agree with all three.
- **Partly satisfied:** one of the three is missing, weak, or only true in some
  cases. Say which.
- **Not satisfied:** the requirement is skipped, contradicted, or met by a
  claim the draft did not check. Say what is missing.

Then check the draft as a whole:

- **Goal.** Walk the flow start to finish as the person who uses the result.
  Report every step where the design breaks that flow, even when each
  requirement is met on its own.
- **Approach.** Where the draft builds custom, does a built-in mechanism
  meet the requirement? Name it. Where the owner chose a specialized
  approach, does the draft follow it?

  any community claim shape the design without a recorded check? Open the
  sources behind the claims that carry the most weight.

## What the focus is for

The current focus is the first thing the next session reads: the session
briefing includes it. It says what is happening now and where the next
session starts. It never repeats the tracker: a work item's status, tasks,
and history stay in the work item.

| Backend | Where the focus lives |
| --- | --- |
| Built-in | `.memory/CURRENT_FOCUS.md` in the main checkout |
| Hindsight | The document `focus` in the project's bank |
| Notion | The "Current focus" page under the project's page |

The same commands read and save it in every backend. Never edit the file or
the page by hand.

## The format

The model's format: a `# Current focus` title line, a `Last updated:` line,
then exactly four `##` sections in this order, under 50 lines in total.

```markdown
# Current focus

Last updated: <YYYY-MM-DD>, <source>, <person or agent>

## Now

## Waiting on the owner

## Untracked to-dos

## Next session starts with
```

What the command enforces:

- It refuses a focus that lacks one of the four sections, has another
  section, or is over 50 lines (exit code 2, nothing saved).
- It adds the title line or the `Last updated:` line when either is missing,
  and sets an older date to today. It cannot know the source or who wrote
  it, so write the line yourself.

## What goes in each section

- **Last updated:** the date, the source (for example `handoff`,
  `work-finish`, `chat`), and who wrote it (a person, or `agent`). Change it
  on every save.
- **Now:** the current outcome or area, with work item ids and titles only,
  for example `- WI-012 CSV export`. Never a status or a stage: the tracker
  holds those.
- **Waiting on the owner:** a decision or action only the owner can take
  that has no work item: what it is, who needs it, and when to check again.
  Work items that wait on him are listed by `toolkit work decisions`, not
  here. A setup step (trust the hooks in Codex, sign in to Notion with
  `ntn login`) stays only while `toolkit doctor` still reports it.
- **Untracked to-dos:** things the owner asked for that have no work item.
  When one becomes a work item, replace the line with the item's id under
  Now.
- **Next session starts with:** one entry: where to resume, what to read,
  and the next action. It is replaced at each handoff, not added to.
- Write "None." in a section with nothing in it.
- Keep it under 50 lines by replacing stale lines, never by appending. Never
  drop an owner to-do that is still open on
