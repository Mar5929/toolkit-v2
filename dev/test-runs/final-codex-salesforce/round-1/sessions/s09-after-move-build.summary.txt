# Permission Sets in Git

A permission set retrieve is complete since API 40.0. A permission set deploy replaces the whole component: any grant missing from the file is disabled.

- Bring a permission set into git only with `permsets.py fetch <Name> --org <sandbox>`. Never commit a file that did not verify clean.
- Before relying on retrieves in a new org or after a major release, run `permsets.py verify` on one large permission set.
- Fetch fresh before every edit.
- Before every deploy, run `permsets.py preflight <file> --org <sandbox>`. `sf project deploy validate` and `sf project deploy preview` cannot detect removed grants.
- A preflight receipt expires after 30 minutes. Re-run it before the deploy.
- To remove grants on purpose, re-run the preflight with `--accept-removals`.
- Deploy to a sandbox only, with the owner's yes in the same chat. The owner runs production.
- Never use `--ignore-conflicts` on a permission file.
- Keep `sourceApiVersion` in `sfdx-project.json` equal to the org's version. Re-fetch everything after a version bump.
- Before committing, run `permsets.py check`, then `permsets.py tidy`.
- After every fetch, re-add the grants in `RETRIEVE_BLIND_SPOTS`.
- After a deploy, check every permission set group that contains the set. If its status is not Updated, click Recalculate on the group in Setup.
- Never hand-merge a git conflict in a permission file. Take one side whole, then re-apply the other change.
- Never write an `Activity.` field permission. Use `Task.` or `Event.`.
- Profiles are excluded. Never deploy a profile

# Salesforce component tracker

Keep the deployment records current in the same response as the change.

A project that already uses `engagement/` uses `engagement/deployment/` wherever this skill says `delivery/deployment/`. Do not create a parallel `delivery/` tree. A project with another artifact root keeps these records where it stores deployment records.

## Deployment folder

```
delivery/deployment/
  component-tracker.csv                  one tracker for the whole project
  full-project-deployment-template/
      package.xml                        project-wide manifest; mirrors the tracker
      manual-steps.md                    manual steps for a full project cutover, if needed
  <work-item-id>-<short-name>/  one folder per work item that ships metadata
      DEPLOYMENT-RECORD.md     deployment scope, evidence, and outcome
      package.xml              that item's new and changed components
      destructiveChanges.xml   only if the item removes components
      manual-steps.md          only if the item has manual steps
  <YYYY-MM-DD>-<release-name>/ cutover plan and release notes when needed
```

- One master tracker for the whole project. Never split it per work item.
- `delivery/deployment/full-project-deployment-template/` holds the project-wide manifest and any full-cutover manual steps. Fill the verified API version before first use.

- Keep work-item folders flat under `delivery/deployment/`. The tracker owns status.
- A manifest (`package.xml`) names the components a Salesforce CLI deploy includes.

# Work check

Voice: write to the owner in plain English. Claude Code: follow the project's Plain English output style. Codex: follow the "How to write replies" section of `AGENTS.md`.
Checks a finished build against every requirement with an independent checker, fixes what fails, and asks the owner to approve the result; it never merges, deploys, or marks Done. Track these steps with the host's plan tool (Claude Code: the task list; Codex: `update_plan`), not in the reply.

## Steps

1. Find the item as `work-on` does: the id he named, this worktree's item, or a title that matches; two matches, ask one question naming both. Read the requirements, the Acceptance list, the Tasks, and the design's Acceptance checks; a sub-item with no design of its own is checked against its parent's (`references/testing.md`, section 1). Then set the testing stage.
   `toolkit work show <id>`
   `toolkit work design <id>`
   `toolkit work set <id> --stage 09-testing`
2. Run the project's tests and every acceptance check the item lists. Several scenarios or manual steps: write a test plan in `tests/` on the item's branch (`references/testing.md`, sections 2 and 3).
3. Brief the `acceptance-checker`, never the agent that built it, naming the branch and the exact commit (`references/testing.md`, section 4).
4. Failures: run the check and fix loop until clean, or until a failure needs an owner decision (`references/testing.md`, section 5).
   `toolkit work set <id> --stage 10-bug-fixing`
5. Record what was checked, the evidence, and the gaps.
   `toolkit work history <id> --note 'Checked: <what>; evidence: <where>; gaps: <gaps or none>'`
6. Ask for the result approval with the checklist in `references/approvals.md`, section 4: stage 11, the item waiting on the owner, the result shown as "Showing the result" says below, and one question: "Do you approve this result?"
   `toolkit work set <id> --stage 11-user-approval --waiting-on owner`
7. His yes: save his words first, record the approval, hand the item back to the agent, and open `work-finish`. A requirement change goes to `work-requirements`; a fix becomes a task and continues here.
   `toolkit work history <id> --note 'Owner said: <quote>' --effect 'Result approved; work-finish continues.'`
   `toolkit work approve <id> --result --by <owner>`
   `toolkit work set <id> --waiting-on agent`
8. Update the current focus when the item's next step changed (`references/current-focus.md`). End every reply with the approval question, or the exact words that continue.

## Steps

Track these steps in the host's plan tool (Claude Code: the task list; Codex: `update_plan`), not in the reply.

1. Decide the home with the memory criteria (`.memory/memory-criteria.md` with built-in memory, which wins; otherwise `references/memory-criteria.md`). Not memory: send it to its home ("Where other things go" below) and stop.
2. Search for a record that already holds it, and read each hit with its version. The save's duplicate check compares wording, so only this search finds a record the new fact contradicts (for example "Mondays" against "Tuesdays").
   `toolkit memory find '<topic>'`
   `toolkit memory get <key> --json`
3. Read the approval mode and apply "Approval policy" below. When it says ask, ask and wait.
   `toolkit config get memory.approval`
4. Write the description and body in the record format (`references/record-format.md`), then save with the form for the case ("Save forms" below).
5. Exit code 2 saved nothing. Read the "Error:" line. Records listed: the duplicate check. "Changed since it was read": read it again and redo the change. Any other rule: fix the text as the message says. `references/replacing-and-retiring.md`, section 2, has each case.

   `toolkit memory retire <key> --reason '<his words>'`
