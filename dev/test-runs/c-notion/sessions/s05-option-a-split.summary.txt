# Conventions every work skill follows

Every skill in the work plugin follows these rules. A skill's own `SKILL.md`
names the file when a rule matters for a step.

This file is `references/conventions.md` in the work plugin's own folder. From
a skill's `SKILL.md` it is two folders up: `skills/work-on/SKILL.md` and
`references/conventions.md` share the plugin folder. In Codex the plugin
folder is the installed copy, for example
`~/.codex/plugins/cache/toolkit-v2/work/<version>/`, so this file is
`~/.codex/plugins/cache/toolkit-v2/work/<version>/references/conventions.md`.

Four rules that are easy to miss:

- Run each `toolkit` command alone, as its own command (below).
- Never change a work item with a script (Python, Node, `sed -i`, `cat >`).
  Use `toolkit work edit --section` or `--label`, or the file edit tool for
  body text. The hooks refuse the script, so it only wastes a step.
- Temporary text goes in `--text`, or in a file in a new `mktemp -d` folder,
  never at a fixed name such as `/tmp/wi001.md`.
- End every reply to the owner with the one question he must answer, or with
  the exact words that continue the work ("Say 'keep going' and I'll start the
  build."). Never end on "The next step is ..." with nothing for him to do.

- Put each `toolkit` command on its own line and run it as a plain command.

  heredoc, `cd ... &&`) or run from a script (for example Python's

  alone, as its own command.

- Exit codes: `0` done; `1` error; `2` validation failure (fix what it names
  and run it again); `3` not supported for this tracker or memory backend

- "saved but not verified" in the output means the write happened and the
  read-back failed. The message names the first line that differs. Lead the
  reply to the owner with "Saved but not verified", say which line, and read
  the item back to judge it.

# TV2-001: Write a short project brief in README.md — solution design

**Requirements:** TV2-001  
**Design status:** Proposed  
**Requirements checked:** TV2-001 Requirements, 2026-09-27  
**Last updated:** 2026-09-27  
**Design approval:** Pending

## What this design solves

People new to Node who clone the repository need a short brief at the top of README.md. It must tell them what `quote.js` does, how to run it, and how to add a quote. This design changes only the README; changes to the script belong to another item.

## Requirements and design readiness

R-01 through R-04 are finalized and ready for this documentation change. No requirement question remains open. The owner requested two options before another README edit.

| Requirement | Status in work item | Design coverage | Remaining decision or gap |
|---|---|---|---|
| R-01 — Audience and placement | Finalized | Both options put a brief with short bullets first. | Choose the layout. |
| R-02 — What the script does | Finalized | Both options describe the random selection and terminal output. | None. |
| R-03 — How to run it | Finalized | Both options give `node quote.js`, Node.js, and repository root. | None. |
| R-04 — How to add a quote | Finalized | Both options name the `quotes` list and its string entries. | None. |

## What exists today

The main checkout's README starts with a title and a paragraph, then Purpose, Start here, Project records, and Project checks and release. It explains running the script but does not explain adding a quote or identify new Node users as the audience. The earlier item worktree has an unapproved README commit, e8c9796, which the owner declined. In `quote.js`, `quotes` is an array of quoted strings; the script selects an array entry with `Math.random()` and prints it with `console.log()`.

## Constraints and assumptions

| Type | Constraint or assumption | Source and status | Effect on the design |
|---|---|---|---|
| Constraint | The new brief uses short bullet points. | R-01; approved 2026-09-27 | Both options use bullets. |
| Constraint | The brief goes at the top of README.md, before the existing sections. | R-01; approved 2026-09-27 | Keep the rest of the main README below it. |
| Constraint | No README edit before the owner chooses a design. | TV2-001 history; owner, 2026-09-27 | These options remain proposals. |
| Assumption | No package installation or build command is needed. | `quote.js` and R-03; checked 2026-09-27 | The run instruction contains only the Node.js prerequisite and command. |

## Design options

### Option A — One short brief

#### Approach

Add one “Project brief” heading below the existing title, followed by four bullets. Each bullet answers one part of R-01 through R-04. Leave the existing README sections in place below the brief. This adds the fewest headings.

Proposed text:

> ## Project brief  
>   
> - **For:** People new to Node who cloned this repository.  
> - **What it does:** `quote.js` picks one random quote from its `quotes` list and prints it to the terminal.  
> - **Run it:** Install Node.js, then run `node quote.js` from the repository root.  
> - **Add a quote:** In `quote.js`, add another quoted string as an entry in the `quotes` list.

const DESIGN_STATUS_LINE_RE = /^(\*\*Design status:\*\*|Status:)([ \t]*)(.*?)([ \t]*)$/m;

/** The design's status line: { label, value } ("**Design status:**" or an older "Status:" line), or null. */
export function designStatusLine(body) {
  const m = DESIGN_STATUS_LINE_RE.exec(String(body ?? ''));
  return m ? { label: m[1].replace(/\*/g, ''), value: m[3].trim() } : null;
}

/**
 * The frontmatter status (proposed, approved, superseded) a design body's
 * status line gives, or null when there is no line or it is still a prompt.
 * Draft and In review are a proposed design.
 */
export function designStatusFromBody(body) {
  const line = designStatusLine(body);
  if (!line || isPlaceholder(line.value)) return null;
  const v = line.value.toLowerCase();
  for (const [status, words] of Object.entries(DESIGN_LINE_WORDS)) if (words.includes(v)) return status;
  return null;
}

/**
 * Keep the design body's header lines in step with the frontmatter:
 * - "**Design status:**": proposed -> Draft (an "In review" already written is
 *   kept), approved -> Approved, superseded -> Superseded. An older "Status:"
 *   line gets the frontmatter word.
 * - "**Design approval:**" (when opts.approved is given): an approval
 *   "YYYY-MM-DD by <name>" -> "Approved by <name> on YYYY-MM-DD"; no -> Pending.
 */
export function setDesignStatusLine(body, status, opts = {}) {
  let text = String(body ?? '');
  text = text.replace(DESIGN_STATUS_LINE_RE, (all, label, gap, value, tail) => {
    if (label === 'Status:') return `${label}${gap || ' '}${status}${tail}`;
    const words = DESIGN_LINE_WORDS[status];
    if (!words) return all;
    if (!isPlaceholder(value) && words.includes(value.trim().toLowerCase())) return all;
    const word = status === 'proposed' ? 'Draft' : status === 'approved' ? 'Approved' : 'Superseded';
    return `${label}${gap || ' '}${word}${tail}`;
  });
  if (opts.approved !== undefined && opts.approved !== null) {
    const a = parseApproval(opts.approved);
    let want = null;
    if (a.ok && a.approved && a.date && a.by) want = `Approved by ${a.by} on ${a.date}`;
    else if (a.ok && !a.approved) want = 'Pending';

# Publish a documentation save

Save an agreed change to Git-tracked project documents from its own temporary
worktree, and push it straight to the default branch with no pull request.
The project's rule for this is `.claude/rules/publish-project-documents.md`;
its `paths` list names the documents this skill saves.

1. **Confirm it is documentation in an allowed path**, not code, rules, skills,
   hooks, settings, `.memory/`, or `.work-items/` (list below).
2. **Start a save workspace** from the project, with the script in the
   `scripts/` folder beside this `SKILL.md`:

   ```text
   node <this skill's folder>/scripts/publish-docs.mjs start --branch <default-branch> -- <file> [more files]
   ```

   It fetches the remote, creates a separate sparse worktree beside the project,
   and prints its path. Work only in that path for this save.
3. **Make the edit there and stage the files by name.** Read the full staged
   diff. Add `DECISIONS.md` rows only with `toolkit decision add`, run there.
   After a change under `ai-external-knowledge/`, regenerate its index there
   ("Step 3 in detail") and stage `ai-external-knowledge/INDEX.md` too.
4. **Publish** from the save workspace:

   ```text
   node <this skill's folder>/scripts/publish-docs.mjs publish --message "<plain commit message>"
   ```

   It refuses other staged paths, unstaged or untracked files, and conflict
   markers (trailing spaces are fine: two make a Markdown line break); commits;
   pushes without force; and checks the remote has the commit.
5. **Report** the commit id and that it reached the remote. After the task's
   last publish, remove the clean save workspace (`git worktree remove <path>`).

# Work check

Voice: write to the owner in plain English. Claude Code: follow the project's Plain English output style. Codex: follow the "How to write replies" section of `AGENTS.md`.
Shared rules: the work plugin's `references/conventions.md` and `references/helpers.md` (how to brief agents), two folders above this skill's folder (`../../references/`). To open another skill, Claude Code uses the Skill tool; Codex reads that skill's `SKILL.md`. Run each `toolkit` command alone, on its own line: in Codex a command joined by `&&`, `;`, a pipe, or a heredoc, or run from a script, runs inside the sandbox and fails. Give text with `--text`, or a file in a new `mktemp -d` folder (never a fixed `/tmp` name, deleted right after the command). Never change a record with a script.

## Steps

1. Read the requirements, the acceptance list, and the tasks, then set the testing stage. When the show output's "Design:" value is not `none`, also read the design's Acceptance checks (in "Build and verification plan") and the selected option's "How to check it" column (the design command exits 1 for an item with no design). A sub-item whose "Design:" says "none of its own" and names its parent's approved design is checked against that design: read the parent's.
   `toolkit work show <id>`
   `toolkit work design <id>`
   `toolkit work design <parent-id>`
   `toolkit work set <id> --stage 09-testing`
2. Run the project's tests and every acceptance check the item lists. A check with several scenarios or manual steps gets a test plan: a copy of `tests/TEST-PLAN-TEMPLATE.md` named for the item, with the results filled in. A check that could not run is reported as not run, never as passed.
3. Brief the `acceptance-checker` agent (never the agent that built it): one verdict per requirement (met, partly met, not met) with evidence, plus defects seen in the diff. Give it the branch and commit to check.
4. Failures: set the bug-fixing stage; a `builder` agent (or the main agent) fixes; the checker checks again. Repeat until clean, or until a failure needs an owner decision (an Open Questions row and the item waiting on the owner).
   `toolkit work set <id> --stage 10-bug-fixing`
5. Record the result: what was checked, the evidence, the known gaps.
   `toolkit work history <id> --note "Checked: <what>; evidence: <where>; gaps: <gaps or none>"`
6. Set the approval stage and wait on the owner. Show him what it does now, how to see it (a link, a command, or a screenshot), the evidence, and the gaps. Ask one line: "Do you approve this result?"
   `toolkit work set <id> --stage 11-user-approval --waiting-on owner`
7. Yes: record it (the command adds its own history row), quote his words in one note, and hand the item back to the agent unless another question for him is still open; then open `work-finish`. A requirement change goes to `work-requirements`; a fix becomes a task and continues here. Every reply ends with the approval question, or the exact words that continue.
   `toolkit work approve <id> --result --by <owner>`
   `toolkit work history <id> --note "Owner's words: <quote>"`
   `toolkit work set <id> --waiting-on agent`

# Acceptance checker

Check whether a finished result does what the owner asked. You are never the
agent that built it. You run tests and read code, but you change nothing. You
advise; the main agent fixes; the owner approves.

## Start with the brief

- The brief gives the work item id, the requirements (Agreed goal, every
  `R-xx` with its acceptance check, the Acceptance list), the design's
  Acceptance checks table (in its "Build and verification plan") and the
  "How to check it" column of the selected option's Requirement coverage, the
  item's test plan when it has one (a copy of `tests/TEST-PLAN-TEMPLATE.md`),
  the branch or commit to check, and the project's test commands.
- Check that you are looking at the exact code the brief names:

  ```text
  git status
  git rev-parse HEAD
  git log --oneline -5
  ```

  If the commit differs from the one in the brief, say so first.
- When the brief asks for a check before a merge, report the exact commit
  you checked, so the main agent can confirm nothing changed after it.

## Check

- Run the project's tests and every acceptance check you can run. Copy each
  command and its result line exactly.
- For each requirement, give one verdict:
  - **Met:** the acceptance check passed, or the evidence shows the required
    behavior. Name the evidence.
  - **Partly met:** some of the behavior works. Say what is missing.
  - **Not met:** the behavior is missing or wrong. Say what you saw.
  - **Not run:** the check could not run here. Say why and what would run it.
    Never report a check that did not run as passed.
- Read the diff for the item's branch against its base. Report defects you
  see: broken edge cases, missing error handling the requirements ask for,
  behavior the requirements did not ask for, files changed that the design
  did not name, and anything that would ship something unfinished.
- Walk the flow start to finish as the person who uses the result. Report any
  step where it breaks, even when each requirement passes on its own.

requirements, and the design's "Build and verification plan" instead of a
finished result.
