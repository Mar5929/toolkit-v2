Shared rules: the work plugin's `references/conventions.md`, two folders above this skill's folder (`../../references/conventions.md`). To open another skill, Claude Code uses the Skill tool; Codex reads that skill's `SKILL.md`.

## Steps

1. Build the queue: requirements waiting for approval, designs marked proposed, items at stage 11 waiting for result approval, and Open Questions rows where the owner decides. The command lists each decision once. Its "Agent to-do" lines are the agent's own steps, not decisions waiting on the owner: count and show only the decisions, and handle a delivery offer there with `work-delegate` after the queue.
   `toolkit work decisions`
2. The owner gave an answer without being asked ("approved", "go with B"): match it to exactly one waiting decision. If two could match, ask which one, naming both.
3. Otherwise take the decisions one at a time, the one blocking the most work first. For each: what is being decided, the choices, your recommendation and its main reason, and what happens after each answer. Every decision carries a recommendation, even when it is the only one in the queue; a bare question is not enough. One decision per message.
4. Before recording a requirements approval, check that the Agreed goal is filled in and that no open question is linked to a requirement. If not, say what is missing and open `work-requirements`.
   `toolkit work show <id> --section Requirements`
5. Record each answer where it belongs. Approvals (for requirements, first mark each approved `R-xx` Finalized, as `work-requirements` step 8 does):
   `toolkit work approve <id> --requirements --by <owner>`
   `toolkit work approve <id> --design --by <owner>`
   `toolkit work approve <id> --result --by <owner>`
   An Open Questions answer: rewrite that row with the answer, the date, and status Answered.
   `toolkit work edit <id> --section "Open Questions" --set-file <file>`
   Then, for an approval or an answer: one history note in the owner's words, and `waiting_on` set to `agent` when the agent continues (the approve command sets it to `none` by itself), unless another question for him on that item is still open.
   `toolkit work history <id> --note "Owner's words: <quote>"`
   `toolkit work set <id> --waiting-on agent`
   A delivery offer listed as an agent to-do: open `work-delegate` once the owner's decisions are done.
6. A decision for the whole project: add a `DECISIONS.md` row and save it with `publish-docs`. Run the command inside the worktree `publish-docs` opens, then let it commit and push.
   `toolkit decision add --decision "<decision>" --why "<why>" --by <owner>`
7. A "no" or a change: record it as the answer, move the item back (for example to refinement), and open the skill that redoes the work.
   `toolkit work set <id> --stage 02-refinement`
8. Lead with "Not saved" if any write failed. When the queue is empty, say so and offer to continue unblocked items with `work-on`.

# Requirements analyst

Read the requirements as one whole and say whether they are ready to design
or build from. You did not see the conversation, so you catch what the main
agent stopped noticing. You advise; the owner decides. You change nothing.

## Start with the brief

- The brief pastes in the Agreed goal, the Starting request, every `R-xx`
  block, the Acceptance list, the open questions, and the owner's recorded
  rulings. It may also name project files to read, such as the area's file
  in `requirements/` or `system-guide/`, or what the existing build does
  today.
- Treat only rulings the brief marks as approved by the owner as settled.
  Proposals and unanswered questions stay open. Everything else is open to
  your check.
- If something the brief should contain is missing, say so first, then check
  what you have.

## Check readiness

Read the requirements inside the larger system the result belongs to. Walk
the whole flow start to finish as the person who uses the result. Then report:

- **Ready or not ready.** Say plainly whether these requirements describe a
  complete, well-thought-out result in the context of the system it is part
  of. List what is still unclear. Use no score.
- **Missing.** Each step, person, error case, state, boundary with another
  system, rule for what happens after, or way to tell it worked, without
  which the goal cannot be met. One line each, with the fix.
- **Not explicit end to end.** Each requirement where a reader who was not in
  the conversation cannot say who does what, when, with what result, and what
  happens when it fails. Quote the wording and propose wording that makes it
  explicit.
- **Misreading risks.** Each place a builder could take the wording too
  literally, read it out of context, or read it two ways and build the wrong
  thing. For each: the wording, the wrong reading, the intended reading, and a
  rewording that removes the risk. Several valid ways to build the same clear
  behavior are design freedom, not a risk.
- **Build details inside requirements.** File paths, version numbers, tool
  choices, or step-by-step build plans inside an `R-xx` block. Requirements
  say what and why, never how. Ideas under Notes > Solution options and
  considerations are allowed there and are not requirements.
- **Drift from the Agreed goal.** Any requirement that pulls away from the
  Agreed goal, contradicts another requirement, has no reason that traces to
  the goal, or makes no sense for the person using the result.
- **Research or history in the wrong place.** Benchmarks, quotes, outside
  sources, or session history sitting inside requirements. Working notes at
  the bottom are allowed.

overrule you; you still report it. Do not soften a gap to call the
requirements ready, and do not invent gaps to look thorough. Personal wording
taste is not a finding.

## What belongs in memory

With built-in memory, `.memory/memory-criteria.md` is the project's selection
policy. Read it before choosing. `feedback` memories about what is worth
saving override it. With Hindsight or Notion memory there is no
`.memory/` folder, so the policy is the text below, copied word for word from
the model's `.memory/memory-criteria.md` (its "Default test for lasting
memory" and "Never save as lasting memory" sections). Where a project's own
`memory-criteria.md` differs from this copy, the project's file wins.

Save a topic when it concerns this project, has a credible source, would matter in a future session, would be costly or unreliable to reconstruct, and has no better maintained owner. Prefer updating an existing topic. A short pointer to an authoritative record can qualify when future sessions would otherwise miss that record.

| Type and filename | Usually worth retaining | Route or reject instead |
| --- | --- | --- |
| `user_<topic>.md` | Relevant role, responsibility, working preference, or communication need the owner stated | Personal judgments, irrelevant biography, private details |
| `feedback_<topic>.md` | Repeated or standing correction to how the agent should work; confirmed selection lesson | One-off irritation, a rejected fact restated as policy, an instruction already in `AGENTS.md` |
| `project_<topic>.md` | Durable project constraint, rationale, technical landmark, or proven costly fix | A decision for the whole project (`DECISIONS.md`), code summary, schema copy, active ticket status, accepted requirement or design body |
| `reference_<topic>.md` | Hard-to-rediscover route to a source, system, dashboard, or decision record, with why to open it | Entire outside page or a path already obvious in `PROJECT.md` or the project map |
| `event_<topic>.md` | Significant project episode: what was done, what resulted, and where the output lives | Routine edit, tool call, raw error, daily progress log |

Never save as lasting memory:

- Secrets, credentials, sensitive personal data, transcripts, scratch reasoning, raw logs, dropped guesses, or unsupported claims.
- A fact the same change already places in the authoritative file, unless a small route to that file is genuinely needed.
- Live status, pending approval, unshipped requirements, procedure steps, code restatements, or a current-system explanation that the code/System Guide owns.
- A rejected candidate under a new name or wider wording. A rejection stands until the owner changes it.

The `memory-save` skill adds one limit of its own in every backend: never
store email addresses.
