# Independent reading of the original Toolkit instructions

I read only the original snapshot at `/tmp/tkv64-original`. I used its root guide and evaluation and clarity rules, the project-setup entry and its update, setup-copy, and finishing routes, and the delivered guides and skills needed for these four situations. I did not inspect revised files or other reviewers' findings. The actions below are simulations; I made no project, Git, Notion, or Hindsight changes.

## A meeting in a project with Hindsight memory and Notion work items

I would read the project's `PROJECT.md` for its bank, tracker IDs, people, and decision authority, then read the Hindsight rule and Notion tracker procedure. Hindsight's installed override means that I would use the tracker and project records for current work. I would neither create `memory/CURRENT_STATE.md` nor report its absence as a fault.

I would search for the meeting source before filing it unchanged in `sources/` and indexing it. A new SRC number becomes usable only after `publish-docs` publishes its save on the default branch. I would distinguish what somebody said in a meeting from a confirmed decision. `file-source.md` says to keep a source's decision Open until a person who may decide confirms it; `record-decision.md` likewise distinguishes authorized answers from source claims. I would record the shared decision or open question in `DECISIONS.md`, preserve its source and reason, identify the existing affected work items, and add any applicable system rule through the system-document procedure. After publication, I would link its IDs in the affected Notion work items without copying the decision into each item. Changed approved requirements need the requirements-change procedure.

I would preserve an overdue unresolved deadline as overdue and unresolved. If a named person owes an action, I would save the task immediately in the relevant work item, or as a project task when no work item owns it, keeping the original due date and the responsible person. Passing the date does not prove completion or cancellation. I would report who still owes the task and what happens next, without inventing a new date.

I would review the lesson against Hindsight's lasting-memory criteria, search and read related memory before saving, and deliberately save qualifying context with source, date, and any published record pointer. I would identify an unproven lesson as unproven and keep ordinary work status in Notion. The default Hindsight package does not save the session automatically. A memory save would not give permission to build, merge, or deploy.

The original routing is unclear in two places. First, `file-source.md` sends every date or deadline to `managing-project-memory`, while Hindsight forbids routine status and facts that matter only for the moment and says current work belongs in the tracker. The Hindsight replacement instruction tells me to use the tracker, but it does not explicitly say where a deadline with no action item belongs. I can place an actual action in a task; I cannot derive a precise tracker form for a standalone dated event from that route alone. Second, `file-source.md`, under “When no work item is open for the source,” tells me to list requests, decisions, and questions and do those the owner chooses, while the root guide says to file new facts and correct records in the same turn without asking. A reader could either file a shared Open entry immediately or wait for the owner's choice.

## A named build and team were authorized before the design finished

I would preserve the existing authorization as an answered Questions and Answers row, including the owner's words and its scope. I would not repeat the delivery offer or team-arrangement question. `building.md` accepts an owner's own “you drive” as authorization, says to settle the team arrangement only if the owner's words did not already choose it, and says its answers hold across sessions.

I would still ensure that the requirements and selected design are approved. “Design complete” alone is not the owner's design choice. If design approval is missing, I would present the finished options and ask for the required choice. If the owner has chosen the design without changing requirements, I would record that choice, approve the design, turn its build order into tasks without replacing existing IDs or phases, and move the work item to Building. Once those conditions are satisfied, the existing build and team authorization allows me to start ready tasks and authorized helpers, maintaining one writer per file and verifying each return. It does not authorize a default-branch merge or deployment by itself.

The literal original process would nevertheless stop me at `designing.md`, step 12: “Stop” and “Say 'keep going' and I'll start the build.” It offers no exception for a build already authorized. That is an unnecessary new gate for this situation. The root evaluation rule says to do the work when there is nothing to raise, and the build procedure preserves prior authorization, so the design ending conflicts with both.

The lifecycle's “Record the owner's yes only when the owner answers the question you asked” is also narrower than the root guide's “When the owner's own words state the change, those words are the yes” and the build procedure's own-words delivery exception. A stranger cannot apply those sentences uniformly when the owner proactively names several approved steps. I would preserve the owner's exact words and make clear which approvals they actually cover rather than interpreting build authorization as approval of an unseen design.

## Checking a local setup with intact records and a missing template

I would read the recorded setup choices, build a temporary setup copy for those choices, compare the toolkit files, and run the applicable final checks. I would not make an update worktree, overwrite existing records, change the owner's setup choices, or replace differences merely because the installed toolkit differs.

If the missing template is one listed in `finishing.md`, under “The final checks in 'check the setup',” I would restore it from the setup copy into the main checkout with the non-overwriting copy specified there. For example, I would restore `work-items/work-item-template/DESIGN.md` when local work items are selected. The same explicit permission applies to `WORK-ITEM.md` and the listed local guides and memory template. I would report each restored file. Existing work items, task records, and memory records remain intact. The local session-start hook may rebuild the generated `memory/MEMORY.md` index. I would report other differences and failed checks with recommended fixes, then remove the temporary setup copy.

This route is sufficiently explicit for the named missing-template case. The broad instruction “Change nothing” has the two stated exceptions, so restoration is not an update requiring a further question. A missing template outside the listed local paths would only be reported and recommended for repair. The restoration command assumes its parent folder exists; if the folder is missing too, I would need to interpret whether making the directory is part of putting the named template back. That directory detail is not stated.

## Closing an item whose decision affects other items, with Git publication blocked

I would read the current work item and its existing decisions, design, related items, lessons, and closure evidence. I would identify the shared decision and all affected existing items, search for an existing authoritative record, and follow `filing-project-records` rather than copy its text among work items. The closing procedure expressly asks whether such material should be kept for the whole project, so on the literal original path I would record its proposed disposition and ask “Do these move up as listed?” unless an applicable closing answer already covered it.

After the required authorization, I would write and check the record in the document-save worktree and attempt its normal publication. If publication is blocked by branch protection, account access, or a conflict that safe recovery cannot settle, I would keep the save worktree and its commit, report separately what is written, checked, committed, and published, and put the precise remaining action in the item's Current state. I would neither bypass protection nor try another account. For a Hindsight project, I would record current pending work in the tracker rather than create a local Current State file.

I would not mark the shared decision “Filed as DEC-###,” insert its reserved ID into affected Notion work items, claim that its Moved up line is complete, or mark the item Done while publication remains required. The original rules say the ID is ours only when the save reaches the default branch. When that succeeds, I would verify publication, link the decision and system-rule IDs to affected items, handle any requirement changes, finish the Moved up line, and continue through the applicable Done approval. If publication succeeded but only the main checkout update were blocked, that is a different case: the save is finished, Notion links may be written, and local work-item links must wait for the main checkout.

The safety and ID boundary are clear. The timing of shared filing is not: the root guide says to save new shared facts and correct wrong records in the same turn without asking, while closing requires approval to “move up” a decision, rule, term, or lesson. Earlier filing routes also promote shared decisions before closure. That leaves a reader unsure whether a confirmed decision discovered at closure needs a new permission, or whether this question only approves an unconfirmed proposal. “Moved up” adds a project-specific label for an ordinary filing action; its local explanation helps, but it can conceal this approval distinction.

## Overall result

The original instructions support safe record preservation, deliberate Hindsight saves, local-template restoration, and recovery from blocked document publication. They do not give one consistent answer for continuing an already authorized build after design approval, for deciding when a confirmed shared fact needs another permission, or for placing a standalone overdue deadline in a Hindsight project. Those are actionable reading failures rather than failures to understand the owner's goal.
