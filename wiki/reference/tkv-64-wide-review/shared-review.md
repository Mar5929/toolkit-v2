## Confirmed issues

1. **P2 — Write-only builder fallback cannot follow its return procedure.** `.claude/skills/managing-work-items/references/builder-brief.md:9` supports a builder editing the work item's own worktree with `Commit: no`. `building.md:99` still requires a separate worktree; `building.md:108–109` requires testing the helper branch, merging it, then removing its worktree and branch. Trigger: a host allows helper edits but not helper worktree creation/commits. The returned changes are uncommitted in the item's own worktree, with no separate branch to merge or safely remove. The main process lacks its documented fallback's integration step. Remedy: integrate returned edits in their actual location under the main agent's permissions; verify and commit them there, and merge/remove only a distinct helper branch/worktree. Keep the ownership boundaries and independent verification.

2. **P2 — Source quotation instructions contradict each other.** `sources/AGENTS.md:39` forbids copying any source text into a work item, decision, or system document. `refining-requirements.md:111` requires a source's words in Original verbatim requirement; `file-source.md` likewise calls for requests in the source's words. Trigger: a transcript says “export only approved invoices.” Recording the required verbatim requirement violates the folder rule; omitting it violates the requirement procedure. Remedy: distinguish retaining the immutable complete source from quoting the necessary passage with its SRC and provenance. Preserve immutable originals and avoid duplicate whole sources.

3. **P2 — Chosen non-origin remote is ignored.** `.claude/skills/pull-latest/SKILL.md:21–23` asks which remote to pull from, but `:35–38`, `:45`, and `:55–58` continue to use `origin`. `.claude/skills/reset-to-remote/SKILL.md:29` asks for the source remote, but `:38` and `:53` still resolve `origin`. Trigger: the repository has only `upstream` and the owner selects it. The next default-branch command addresses a nonexistent remote, so the approved workflow cannot proceed as written. Remedy: carry the verified selected remote through fetch, default-branch resolution, targets and reports. This does not require renaming the remote. `publish-docs` already has a distinct explicit recovery route; this finding is not about that route.

4. **P2 — Resolving an explicit PR starts from the current branch instead.** `.claude/skills/merge-and-clean-up/SKILL.md:32` runs bare `gh pr view`, while `:59` accepts a number or URL as the clear requested PR. Trigger: the owner says “merge #14” while the current branch has #15. The first read selects #15 or fails to find the requested PR. Subsequent head checks may prevent unsafe action, but they do not restore the owner's requested selection. Remedy: resolve the supplied number/URL and repository first, retaining that identity for subsequent reads. Use branch inference only when no explicit selection was supplied. GitHub documents the current-branch default in [gh pr view](https://cli.github.com/manual/gh_pr_view).

5. **P2 — Merge overlap check compares the default branch instead of the PR base.** `merge-and-clean-up/SKILL.md:93–101` calls the default-to-head comparison “the files that the pull request changes,” although `:41` records the actual base. Trigger: a PR targets `release`, which contains a config change absent from `main`; the PR itself changes only documentation. Comparing `origin/main...head` includes the release config, and an unrelated dirty config in the main checkout produces a false overlap and unnecessary owner stop. Remedy: obtain the actual PR changed files against its recorded base/head, for example using the PR diff already used for forks. Separately check the files affected by any planned checkout update. Git documents the merge-base meaning of the three-dot comparison in [git diff](https://git-scm.com/docs/git-diff).

6. **P2 — Requirements analyst brief omits configured wiki evidence.** `requirements-analyst-brief.md:25–29` provides answered Q&A as verified decisions and local `system/` as system context; `:38` says check only the supplied material. The main agent correctly retrieves Notion wiki/pending captures in `refining-requirements.md:28`, but the helper template does not carry that evidence forward. Trigger: after verified wiki cutover, the cancellation policy was amended in Product Wiki and is absent from the current item's Q&A; the historical local policy remains. A fresh analyst receiving only the filled standard brief is directed to the old policy. Remedy: pass applicable configured project records and relevant pending evidence, with direct read access or fresh excerpts and their status/provenance. Retain local inputs for local/Hindsight and unfinished migrations. This is a context gap, not a claim that every main agent necessarily loses the evidence.

## Policy simplifications for owner review

These are inherited prescriptions, not additional routing regressions. They may reflect intentional workflow choices; do not change them silently.

- `lifecycle-rules.md:167–170` requires an exact spoken sentence and exact “Is that right?”; `testing-loop.md:78` similarly requires an exact result question. Preserve understandable scope, evidence and approval, while allowing natural wording when exact text serves no record/tool contract.
- `refining-requirements.md:83` changes presentation above three findings; `designing.md:27` escalates after two dispute rounds; `handoff/SKILL.md:92` forbids a third verifier. The confirmed design principle favors judgment over arbitrary limits. State the purpose of grouping or escalation and use whether the disagreement needs an owner decision or independent verification. Keep meaningful verification; do not substitute an arbitrary new count.
- Local steps that say ask again can obscure the global same-scope authorization exception. Root `AGENTS.md:123` and lifecycle authorization rules do supply that exception, so this is not proof that an already-authorized action must be reapproved. A general instruction to apply existing authorization at approval gates would make the process easier to follow than adding individual exceptions.
