# Local Work-Item Folders

This project tracks work in local folders under `.work-items/`: Git-ignored, in the main checkout, and shared by every worktree. Git does not back it up; `toolkit export` is the backup. Sub-items, groups, `archive/`, and the folders the tracker ignores: the `work-organize` skill.

## Finding and creating items

- An item is a folder holding a record, `WORK-ITEM.md`, and `DESIGN.md` when a design exists. The frontmatter `id` (for example `WI-001`) is the item's identity. The folder name and the file name may change.
- Find an item's files with `toolkit work show <id> --path`. Never guess a path.
- Create items only with `toolkit work new`. It takes the next ID under a lock, so parallel sessions never pick the same one. IDs are never reused.

## When the owner moves folders

- The owner may move, rename, nest, or group item folders by hand. `toolkit work sync` finds every item again by its ID; the session hooks and every `toolkit work` command run it. Report what moved and continue.
- Use the `work-organize` skill to reconcile anything the sync reports as missing or duplicated.
- Never move, group, archive, or rename items on your own initiative. When the owner asks, use `toolkit work move <id> --under <id|group|archive|root>`.

## Editing items

- Change frontmatter fields (stage, status, parent, waiting on, approvals) only with `toolkit work` commands. Edit body sections directly or with `toolkit work edit`; the hook checks the record after each edit.
- Never edit `DASHBOARD.md` (generated by `toolkit work sync`) or `.toolkit-state.json` (the ID-to-path map and the highest ID used, kept by `toolkit work`) by hand.
- Keep any other files the owner put in an item folder.
