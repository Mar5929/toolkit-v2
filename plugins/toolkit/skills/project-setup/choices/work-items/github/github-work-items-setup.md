# Work items in GitHub Issues

Follow these steps when the owner answers "GitHub Issues" to question 5 of the guide, [SKILL.md](../../../SKILL.md). The job is done when every check in [reference/github-work-items-checks.md](reference/github-work-items-checks.md) passes.

## Steps

Do steps 1 to 5 right after the answer, before the next question of the guide. Do steps 6 to 10 when the choice's sign-in is done and the owner has named the repository. Do steps 11 to 14 when setup finishes, in Step 6 of the guide.

1. **Tell the owner how the toolkit sets up work items in GitHub Issues by default, and ask whether that is what the owner wants.** [reference/github-work-items-default.md](reference/github-work-items-default.md) holds the default. [SKILL.md](../../../SKILL.md), "Each choice has questions of its own", gives the words of the question and what to ask after a no.
2. **Check the sign-in of `gh`, the GitHub command-line tool.** Ask the owner for the sign-in as soon as the owner picks GitHub Issues, so that the owner can run `gh auth login` while the interview goes on. Never ask the owner for a token. [reference/github-sign-in.md](reference/github-sign-in.md) gives the check and what to ask the owner for.
3. **Ask the owner which repository holds the work items.** Recommend the project's own repository, which `git remote get-url origin` shows. Use only the name the owner confirms.
4. **Copy the choice's files into the project.** The folder `choices/work-items/github/files-to-add/` holds them at the paths a project has them. [reference/what-github-work-items-add-to-a-project.md](reference/what-github-work-items-add-to-a-project.md) lists them, and [reference/placing-files.md](../../../reference/placing-files.md) gives the copy command and what to do with a file that the project already has.
5. **Write `github` on the Tracker line of `PROJECT.md`.** [reference/what-github-work-items-add-to-a-project.md](reference/what-github-work-items-add-to-a-project.md) gives the line.
6. **Check the repository, and create one only after the owner's yes.** [reference/github-repository-for-work-items.md](reference/github-repository-for-work-items.md) gives the yes that everything made in GitHub needs, the command for the check, and what to ask the owner when the repository does not exist or has issues turned off.
7. **Record the repository in `PROJECT.md`.** [reference/what-github-work-items-add-to-a-project.md](reference/what-github-work-items-add-to-a-project.md) gives the line and the place where it goes.
8. **Create the labels that the repository does not have yet, after the owner's yes.** [files-to-add/.claude/skills/managing-work-items/references/work-tracker-labels.md](files-to-add/.claude/skills/managing-work-items/references/work-tracker-labels.md), "Creating the labels", gives the question to ask the owner and the commands.
9. **Run this choice's checks.** [reference/github-work-items-checks.md](reference/github-work-items-checks.md) gives them.
10. **Tell the owner concisely how the work items are kept.** Say where the work items are kept (the repository's Issues page), that each work item is one issue with its State and approvals as labels, and that the owner may edit issues, labels, and sub-issues in the browser, and that the agent notices and carries on.
11. **After the owner's yes, write the project's phases from question 12 as milestones of the repository.** Tell the owner which milestones will be made, because the yes for the labels and the repository does not cover them. The project's `managing-work-items` skill says how, in [files-to-add/.claude/skills/managing-work-items/references/work-tracker-project-roadmap-and-tasks.md](files-to-add/.claude/skills/managing-work-items/references/work-tracker-project-roadmap-and-tasks.md). [reference/finishing.md](../../../reference/finishing.md), "The roadmap", gives the rules for the roadmap.
12. **Run this choice's checks again.** [reference/github-work-items-checks.md](reference/github-work-items-checks.md) gives them. [reference/finishing.md](../../../reference/finishing.md), "Final checks", says how to run a check and what to do when one fails.
13. **Tell the owner the step that only the owner does.** The owner runs `gh auth login` in a terminal, when `gh auth status` shows no sign-in. [reference/finishing.md](../../../reference/finishing.md), "The owner's steps", says how to tell the owner a step.
14. **After the setup commit, ask the push question.** [reference/finishing.md](../../../reference/finishing.md), "The commit offer", gives the question and says when to ask it.

When a `gh` call fails, open [files-to-add/.claude/skills/managing-work-items/references/work-tracker-gh-commands.md](files-to-add/.claude/skills/managing-work-items/references/work-tracker-gh-commands.md), "When a call fails".

For "update the toolkit", follow [reference/updating-a-project-with-github-work-items.md](reference/updating-a-project-with-github-work-items.md). "Check the setup" and a change of where work items are kept use the steps above: steps 4, 5, and 7 give the folder and the lines that this choice adds, steps 6 and 8 give what it makes in GitHub, and step 9 gives its checks. [reference/update.md](../../../reference/update.md) says how each of those jobs works.
